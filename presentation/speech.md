# Текст защиты (5 минут)

**Слайд 1.** Здравствуйте, мы — команда ticket-router. Наш кейс — автоматическая
маршрутизация обращений в службу IT-поддержки: модель по теме и тексту
обращения предлагает, в какое подразделение его направить.

**Слайд 2.** Важная деталь постановки: мы не заменяем оператора, а помогаем ему.
Модель подсказывает очередь, человек подтверждает. Это делает внедрение
реалистичным даже при умеренном качестве классификатора. Метрика — macro-F1,
потому что классы несбалансированы и accuracy маскировала бы игнорирование
редких очередей.

**Слайд 3.** Данные — 28 587 синтетических тикетов с Kaggle, десять очередей,
два языка. Валидация нашла: 13 процентов тикетов без темы, дубликатов нет.
Целостность данных защищена проверкой sha256 при загрузке.

**Слайд 4.** Архитектура — два контура. Офлайн: обучение pipeline, который
сохраняется одним артефактом — предобработка на инференсе гарантированно
совпадает с обучением. Онлайн: FastAPI-сервис с эндпоинтами predict, health
и metrics. Ключевое решение — признаки только subject и body: колонки answer,
type, priority недоступны в момент маршрутизации, их использование было бы
утечкой данных.

**Слайд 5.** Стек сознательно простой: scikit-learn на CPU, FastAPI, pytest,
uv для воспроизводимости. Для учебного кейса интерпретируемость и скорость
итераций важнее нейросетей.

**Слайд 6.** Схема экспериментов честная: одно фиксированное разбиение для всех
моделей, выбор конфигурации по validation, тест — один раз после выбора.

**Слайд 7.** Пять экспериментов: baseline, логрегрессия на словах, с добавлением
символьных n-грамм, LinearSVC и LinearSVC с подбором C по кросс-валидации.
Лучший — LinearSVC с C=10: 0.619 macro-F1 на validation, подбор добавил плюс
0.015. Демо системы — веб-страница с имитацией чата, подход коллег, но
обращается к тому же боевому эндпоинту.

**Слайд 8.** На тесте — 0.619 macro-F1; baseline на validation — 0.045.
На английском 0.70, на немецком 0.49. Для сравнения:
baseline даёт accuracy 0.29, но это бесполезно — он всегда предсказывает самый
частый класс.

**Слайд 9.** Анализ ошибок показал главную проблему: ошибки концентрируются
в кластере классов поддержки — Technical, Product, IT Support семантически
пересекаются, основных пар ошибок — сотни тикетов. И второе: на немецком
качество ниже на 0.21 macro-F1 — словная TF-IDF почти не делит лексику
между языками.

**Слайд 10.** Тестирование: 17 автотестов — данные, пайплайн, API, веб-демо, включая
readiness-проверку без модели. Найдены и
зафиксированы две проблемы: пропуски тем у 13 процентов тикетов и разрыв
качества между языками — обе подтверждены цифрами.

**Слайд 11.** Деплой: локальный маршрут проверен целиком — от установки
зависимостей до smoke-теста API. Dockerfile описан, но сборка не выполнялась —
в среде разработки не было Docker-демона, мы это честно фиксируем. CI на
GitHub Actions гоняет тесты на каждый push.

**Слайд 12.** Мониторинг: технические счётчики уже реализованы в API, для
модельных метрик — план. Алерт: доля 5xx больше 5 процентов за 5 минут —
проверить артефакт и откатиться на предыдущую версию. Полные тексты обращений
в логи не пишутся.

**Слайд 13.** ИИ-ассистент использовался для каркаса кода и черновиков
документации; команда обязана прогнать тесты, сверить метрики и вычитать
формулировки — чек-лист в отчёте.

**Слайд 14.** Ограничения говорим честно: данные синтетические, классы
пересекаются, немецкий хуже, модель не калибрована.

**Слайд 15.** Вывод: собран связный сквозной кейс с понятными границами.
Следующие шаги — иерархическая классификация кластера поддержки и
многоязычные эмбеддинги. Спасибо, готовы к вопросам.
