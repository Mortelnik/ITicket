# Подготовка к вопросам на защите

Актуализировано 16 ноября 2026 года.

## Почему macro-F1, а не только accuracy?

Число примеров по классам различается примерно в 20 раз. Baseline всегда
выбирает Technical Support: на validation его accuracy — 0.2924,
а macro-F1 — 0.0453. Macro-F1 придаёт равный вес каждой из десяти очередей.

## Какой результат у выбранной модели?

Validation macro-F1 — 0.6188. На test из 4 289 обращений: macro-F1 — 0.6185,
weighted-F1 — 0.6220, accuracy — 0.6228. На английском macro-F1 — 0.7019,
на немецком — 0.4922. Разрыв между языками — 0.2097.
Метрики относятся к синтетическому датасету, качество на реальных тикетах
пока не измерено.

## Что дал тюнинг и что здесь означает fine-tuning?

Для LinearSVC подбирали C из значений 1, 5, 10 и 20 через GridSearchCV
с тремя блоками только внутри train. Лучший C — 10. Validation macro-F1
вырос с 0.6043 до 0.6188, прирост — 0.0145. После этого сравнивали
конфигурации по validation. Test в настройке не участвовал.
Здесь речь о настройке гиперпараметров, дообучения нейросетевой модели нет.
Решения о тюнинге и выборе модели принимал человек.

## Как предотвращали утечку данных?

Признаки — только subject и body. Ответ, приоритет и теги исключены как
недоступные при первичной маршрутизации. Векторизаторы обучаются внутри
pipeline только на train. Все модели используют одно стратифицированное
разбиение 70/15/15, seed=42. По сохранённому аудиту точных текстовых
пересечений нет, но одна пара train/test совпадает после нормализации
регистра и пробелов. Этот риск нужно устранить до следующего обучения.

## Почему модель ошибается?

В сохранённой матрице ошибок Product Support определяется как Technical
Support 175 раз, обратная ошибка встречается 148 раз. Семантическое
пересечение очередей — возможная причина. Причины языкового разрыва
отдельно не доказаны. Следующие шаги — уточнение правил разметки,
пилот на реальных данных и проверка многоязычных признаков.

## Почему не использовали BERT или другую нейросеть?

Для учебного проекта сравнили пять конфигураций, которые работают на CPU.
TF-IDF и линейные модели позволяют быстро воспроизводить эксперименты.
Трансформеры в текущем сравнении не участвовали, поэтому их выигрыш или
проигрыш мы не утверждаем.

## Какие автотесты есть?

На 16 ноября 2026 года проходят 74 теста: данные — 9, ML-пайплайн — 14,
API и веб-демо — 23, защитные механизмы — 28. Проверяем разбиение,
сохранение и загрузку модели, совпадение инференса с pipeline,
три разные темы обращений, ошибки и граничный ввод.
Есть отдельный HTTP smoke-сценарий работающего сервера.

## Что проверяет защита от hammering?

По умолчанию допускается 60 запросов за скользящее окно 60 секунд на IP.
Превышение возвращает 429 и Retry-After. Проверены независимость квот,
истечение окна, ограничение памяти и одновременные запросы.
Квоты локальны для одного процесса. Для нескольких реплик нужен общий
ограничитель. Тест параллельных вызовов не заменяет нагрузочное испытание.

## Как обрабатываются запросы к секретам?

Фильтр проверяет URL до маршрутизации и возвращает пустой HTTP-ответ 444
для .env, .git, ключей и файлов учётных данных. Проверяются вложенные пути,
регистр и повторное URL-кодирование. Это HTTP-статус приложения.
Закрытие соединения без HTTP-ответа, как в nginx return 444, не реализовано.
Защитные механизмы предусмотрел человек, код написал ИИ-ассистент
по этим требованиям.

## Что происходит с русским текстом и пустыми признаками?

Кириллица и нулевой TF-IDF-вектор приводят к 422 без назначения очереди.
Русский язык не поддерживается. Проверка кириллицы не является полноценным
определителем языка: неподдерживаемый язык на латинице может получить очередь.

## Выдаёт ли модель уверенность и что делать с ошибкой?

Выбранный LinearSVC не выдаёт калиброванных вероятностей, поэтому
confidence равен null. Порога уверенности пока нет. В целевом процессе
оператор подтверждает рекомендацию. Ошибка может привести к повторному
перенаправлению и задержке ответа, поэтому бизнес-эффект требует пилота.

## Что подтверждено по деплою и CI?

Локальный API прошёл HTTP smoke-проверку, включая три очереди, четыре
пограничных отказа и метрики. Отдельно проверены 429 и пустой ответ 444.
По исходной презентации команда проверила сборку и запуск Docker-контейнера.
В текущей среде повторный контейнерный запуск недоступен.
Workflow GitHub Actions описывает тесты, аудит, сборку и smoke-проверку.
Успешный удалённый запуск CI отдельно не подтверждён. Деплой —
ответственность человека.

## Как контролировать деградацию после внедрения?

Счётчики запросов, ошибок, отказов, распределение очередей и p95 уже есть
в API. Внешний сборщик и автоматические уведомления не подключены.
Порог 5xx выше 5% за 5 минут при не менее 100 запросах — часть плана.
Качество нужно подтверждать macro-F1 на новой ручной разметке.
Сдвиг распределения предсказаний сам по себе падение качества не доказывает.

## Как распределена работа человека и ИИ?

ИИ подготовил каркас репозитория, код, автотесты и техническую документацию.
Человек отвечал за спецификацию для агентов, проверку бизнес-логики,
предусмотрел защитные механизмы, принимал решения по тюнингу модели.
Деплой, итоговый отчёт, презентация и окончательная приёмка —
ответственность человека.
