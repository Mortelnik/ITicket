# Текст выступления для репетиции

Актуализировано 16 ноября 2026 года. Версия с привязкой к слайдам — [speech.md](speech.md).

Здравствуйте! В современной модели корпоративного управления важную роль играет организация документооборота как между структурными подразделениями компании, так и с внешними контрагентами. Приём и распределение входящей корреспонденции часто входят в обязанности секретарей и делопроизводителей. Часть этих операций выполняется по формализованным правилам и может быть автоматизирована.

В данном проекте команда разработала микросервис диспетчеризации входящих обращений. Его задача — классифицировать сообщение и предложить ответственного за соответствующее направление. Потенциально такой сервис можно интегрировать с корпоративными почтовыми ящиками и популярными системами электронного документооборота, где входящую корреспонденцию необходимо распределять между исполнителями.

В рамках учебного проекта мы реализовали эту задачу с помощью модели классификатора для десяти очередей IT-поддержки. По теме и тексту обращения она предлагает подразделение, а оператор подтверждает рекомендацию. Наша цель — сократить ручную сортировку. Экономию времени пока не измеряли. Основная метрика — macro-F1: она придаёт равный вес всем очередям, включая редкие.

Для учебного проекта мы не располагали подходящим корпусом на русском языке, поэтому использовали доступный открытый датасет на английском и немецком. Он содержит 28 587 синтетических обращений. У 3 838 записей, или 13,4 процента, отсутствует тема. Мы сохраняем такие обращения и используем текст сообщения. Проверяем контрольную сумму и разбиение. Точных пересечений текстов между выборками нет, но одна пара совпадает после нормализации регистра и пробелов. Это остаточный риск.

Архитектура включает обучение и работающий сервис. В обучении сравниваем конфигурации, затем сохраняем TF-IDF и классификатор вместе. При инференсе применяются те же преобразования. В признаки входят только subject и body. Поля ответа, приоритета и тегов исключены, поскольку при первом обращении они ещё недоступны. API проверяет ввод, частоту запросов и обращения к секретам.

Паспорт модели фиксирует её назначение и ограничения. Используем словные и символьные признаки TF-IDF и LinearSVC с параметром C, равным десяти. Поддерживаем только английский и немецкий. На выходе — очередь, а confidence равен null: классификатор не выдаёт калиброванных вероятностей. Качество на реальных обращениях ещё предстоит проверить.

На схеме показан целевой процесс. Клиент вводит тему и текст, сервис проверяет допустимость ввода и предлагает очередь. При отказе обращение требует ручной обработки. В остальных случаях оператор проверяет рекомендацию. Сейчас API возвращает результат, а создание тикета и интеграция с реальной системой поддержки остаются следующим этапом.

Стек состоит из Python, scikit-learn и FastAPI. Модель работает на обычном процессоре и не требует платного внешнего API. Зависимости фиксирует uv.lock. Для проверки используем pytest, для запуска — Uvicorn. Dockerfile описывает контейнер с моделью, а веб-демо обращается к тому же API.

Данные разделены в пропорции 70, 15 и 15 процентов. Это 20 010 обучающих, 4 288 валидационных и 4 289 тестовых обращений. Разбиение едино для всех моделей. Параметр C подбирается трёхблочной кросс-валидацией только внутри train. Затем по validation выбираем конфигурацию. Test используем для финальной оценки и повторной проверки сохранённого артефакта без настройки по нему.

Сравнили пять конфигураций. Baseline, всегда выбирающий самый частый класс, даёт macro-F1 0,0453 на валидации. Логистическая регрессия со словами — 0,4689, с добавлением символов — 0,4909. LinearSVC достигает 0,6043. Подбор C повышает результат до 0,6188. Прирост от настройки составляет 0,0145 macro-F1.

На тестовой выборке выбранная модель получила macro-F1 0,6185. Weighted-F1 равен 0,6220, доля правильных ответов — 62,28 процента. По языкам результат различается: 0,7019 на английском и 0,4922 на немецком. Метрики рассчитаны на всех 4 289 обращениях. Два из них превышают ограничения длины API.

В сохранённой матрице ошибок видны пересечения очередей поддержки. Product Support ошибочно определяется как Technical Support в 175 случаях, обратная ошибка встречается 148 раз. Это указывает на необходимость уточнять границы классов. Слабое качество на немецком также требует отдельного улучшения. Причины языкового разрыва пока остаются гипотезами.

На 16 ноября проходят 74 автотеста: девять для данных, четырнадцать для ML-пайплайна, двадцать три для API и двадцать восемь для защитных механизмов. Проверяем сохранение модели, маршрутизацию, граничный ввод и ошибки. Кириллица получает 422, отсутствие модели — 503. Лимит 60 запросов за минуту на IP возвращает 429, запросы к секретам — пустой HTTP-ответ 444. Бизнес-логику принимает человек. Нагрузочных испытаний пока нет.

Локальный API проверен отдельным HTTP-сценарием: готовность, три очереди, четыре отказа и метрики. Дополнительно проверены ответы 429 и 444 по настоящему HTTP. За деплой отвечает человек. Команда проверила сборку и запуск Docker-контейнера. Workflow GitHub Actions описывает тесты, аудит данных, сборку и smoke-проверку. Успешный удалённый запуск CI отдельно не подтверждаем.

API уже считает запросы, ошибки, отказы, распределение очередей и p95 задержки. Счётчики хранятся в одном процессе. Внешний сборщик и автоматические уведомления ещё не подключены. В плане алертов — более пяти процентов серверных ошибок за пять минут при ста запросах и более. Реакция — проверка причины и при необходимости откат. Качество нужно оценивать на новой ручной разметке.

При разработке использовали практики оркестрации ИИ-агентов: постановку задач по спецификации, разделение работы и проверку результатов человеком. ИИ-ассистент подготовил каркас репозитория, код, автотесты и техническую документацию. Человек задавал спецификацию для агентов, предусмотрел защитные механизмы и проверял бизнес-логику. Настройка LinearSVC и выбор модели, деплой, итоговый отчёт и презентация остаются в ответственности человека. Автоматические проверки помогают приёмке, а решение о готовности принимает команда.

Основные ограничения — синтетические данные и пересечение классов. Качество на немецком ниже на 0,2097 macro-F1. Модель не имеет калиброванных вероятностей и порога уверенности для передачи оператору. Проверка кириллицы не распознаёт все неподдерживаемые языки. Надёжность на реальных данных и эффект для бизнеса требуют отдельного пилота.

Мы собрали прототип с воспроизводимой схемой экспериментов, сохранённой моделью, API и автоматическими проверками. Следующий этап — пилот на обезличенных реальных обращениях, уточнение классов и улучшение качества на немецком. После этого — калибровка и порог передачи оператору. Спасибо! Готовы к вопросам.
