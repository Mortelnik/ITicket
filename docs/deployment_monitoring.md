# Деплой и мониторинг

## Проверенный локальный маршрут

Требуются Python 3.12 и uv; команды выполняются из корня репозитория.

```bash
uv sync --locked
uv run pytest -q
uv run uvicorn ticket_router.api:app --host 127.0.0.1 --port 8000
```

Модель входит в репозиторий. CSV нужен только для обучения и воспроизведения
метрик. Во втором терминале:

```bash
uv run python scripts/smoke_api.py --url http://127.0.0.1:8000
```

Локальный HTTP-сценарий после улучшений проверен 13.11.2026.

## Docker

Запустите Docker Engine / Docker Desktop с Linux-контейнерами.

```bash
docker build -t iticket:local .
docker run -d --name iticket --restart unless-stopped -p 127.0.0.1:8000:8000 iticket:local
docker logs -f iticket
```

Демо: http://localhost:8000/, Swagger: http://localhost:8000/docs.
Модель копируется в образ. Dockerfile использует Python 3.12-slim, uv 0.11.14,
uv.lock, непривилегированного пользователя и healthcheck на **/ready**.
Версия uv фиксирована, базовый Python-образ остаётся обновляемым тегом minor;
полная побитовая воспроизводимость образа не заявляется. .dockerignore
исключает .git, локальное окружение, данные и материалы защиты из контекста.

```bash
uv run python scripts/smoke_api.py
docker inspect --format "{{.State.Health.Status}}" iticket
docker stop iticket
docker rm iticket
```

Локально Docker Engine недоступен. Сборка/запуск контейнера не подтверждены;
проверка uvicorn не выдаётся за проверку Docker. В GitHub Actions добавлены
сборка, запуск контейнера и HTTP smoke-тест. Успешный удалённый CI нужно
подтвердить после публикации изменений.

Docker healthcheck помечает контейнер unhealthy, но сам по себе не
перезапускает работающий процесс. restart unless-stopped помогает при
завершении процесса, а реакция на unhealthy требует оператора/оркестратора.

## Предлагаемый production-маршрут

Это план, в учебном проекте не реализован:

1. CI проверяет тесты, данные, сохранённые метрики, сборку и HTTP-контракт.
2. Доверенный артефакт и зависимости версионируются вместе; перед обновлением
   модель проверяется на фиксированном контрольном наборе.
3. Deployment с readiness на /ready и liveness на /health; трафик поступает
   только после загрузки модели.
4. Сервис за reverse proxy с TLS, ограничением размера тела запроса,
   частоты запросов и согласованными таймаутами. API ограничивает длину
   полей, но не реализует потоковый лимит размера HTTP-тела.
5. JSON-рекомендация интегрируется с тикет-системой. Отказы и спорные случаи
   обрабатывает оператор; автоматическая очередь сообщений пока отсутствует.
6. При сбое — восстановление предыдущего образа вместе с его моделью.

## Реализованные метрики

/metrics отдаёт JSON в памяти одного процесса:

- requests_total, errors_4xx, errors_5xx, error_rate;
- predictions_total и predicted_queues;
- rejected_inputs_total и unsupported_texts_total;
- latency_p95_ms по последним максимум 1000 завершённым запросам,
  latency_sample_size.

Счётчики сбрасываются после рестарта, не агрегируются между репликами.
Запросы health/ready/metrics входят в технические счётчики.
Обработчик не записывает полный текст обращения в логи. Хэширование текста
и журнал решений не реализованы. Доступ к внешнему мониторингу и автоматические
уведомления отсутствуют.

## План мониторинга и алертов

| Сигнал | Условие и реакция |
|---|---|
| Серверные ошибки | Дельта errors_5xx / дельта requests_total > 5% за 5 минут при >=100 запросах: проверить модель, логи и ресурсы, при регрессии откатить образ |
| Неизвестный текст | Дельта unsupported_texts_total / число запросов /predict > 10% за час: проверить язык входа и интеграцию, передать выборку оператору |
| Распределение очередей | Доля самой частой очереди >40% за сутки относительно стартового ориентира около 29%: проверить изменение тем и языков, собрать разметку |
| Задержка | Устойчивый рост p95 относительно измеренного базового уровня: проверить длины запросов и CPU; численный SLA пока не задан |
| Качество модели | На еженедельной независимой разметке считать macro-F1, ошибки по очередям и языкам, долю перенаправлений оператором |

Эти условия — план, не работающая система алертов. Для окон 5 минут/час/сутки
нужен внешний сборщик и хранение временных рядов. Число запросов /predict,
длины, язык входа и исправления операторов нужно добавить в такой сборщик:
текущего JSON недостаточно для всех предложенных алертов. p95 последних
1000 запросов не равен p95 за фиксированные 5 минут.

Контрольная точка офлайн: macro-F1 0.6185, EN 0.7019, DE 0.4922.
Дрейф распределения сам по себе не доказывает падение качества: это проверяется
на новой разметке. Реальные тексты могут содержать персональные данные —
доступ к выборкам ограничивается, чувствительные фрагменты обезличиваются.
